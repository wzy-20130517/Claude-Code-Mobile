# 终端视觉语言规范

首次制定：2026-08-30 · Art Director（vision-auditor）· aicorp #4

这份文件是终端输出**排版与配色的唯一真源**。它存在的目的不是记录当前实现，而是
**终止「同一个空行问题被反复改」的循环**。任何关于空行、前缀、缩进、颜色的争议，
以本文为准；实现与本文冲突时改实现，不改本文——除非在本文的「修订记录」里
写清为什么原规则不成立。

---

## 一、为什么空行规则会被反复改三四次

先给结论，因为这是 CEO 唯一真正关心的问题：

> **不是审美反复，是缺少「行首状态」的单一真源。**
> 三条独立的输出通道各自猜「我现在是不是在行首」，猜错就多一行或少一行；
> 每次修都只教会其中一条通道猜得更准一点，于是换个路径又错，看起来像
> 「审美改来改去」，其实是同一个结构缺陷在不同路径上复发。

从 git 历史能把这条循环完整还原出来（按时间顺序）：

| 提交 | 当时的判据 | 结果 |
|---|---|---|
| `732aadf3` | 「正文首个 chunk 的前导换行要吃掉」 | 修好正文，工具行还错 |
| `89a76bc0` | 「已在行首时前缀不再补前导换行」 | 引入**行首探测** |
| `0a03d3f4` | 「光标已在行首时不再补前导换行」 | 同一判据再抄一遍到工具行 |
| `b91bc0a3` | 加 `leadNewline` 参数，让调用方决定 | 判据从 1 个变成 2 个 |
| `a5b9263a` | 「开窗前必须先 flush 正文」 | 发现顺序也是变量 |
| `3ced82bd` | **「废掉恒真的行首探测」**，改用 `anyOutputEmitted` | 承认探测本身是错的 |
| `e1be2380` | 更新注释：「空行规则已反转」 | 规则方向被推翻 |
| `bc0f3d47` | 「工具结果到正文之间也要空一行」 | 补最后一个漏掉的接缝 |

八次提交，四个不同判据（吃掉前导换行 / 行首探测 / leadNewline 参数 /
anyOutputEmitted 标志），中间还发生过一次**规则反转**。这不是有人品味变了，
是每次都在给症状打补丁：

1. **行首探测不可靠**。终端光标位置只能靠自己记账推算——一旦中间有人
   直接 `process.stdout.write` 绕过记账，探测就恒真或恒假。`3ced82bd` 的
   commit message 里 "恒真的行首探测" 就是实测结论。
2. **三条通道各写一份判断**。正文走 `stream-md` 的 flush，工具行走
   `writeSideChannel`，提示符清理走 `clearPromptLine`，每条都有自己的
   if 判断，改一处不影响另两处。
3. **空行责任方没定死**。到底是「上一段负责在结尾留空」还是「下一段负责在
   开头补空」，历史上两种都实现过（`732aadf3` 是前者，`0a03d3f4` 是后者），
   两者混用必然出现 0 行或 2 行。

所以规范的第一条不是「空几行」，而是**空行由谁负责、状态记在哪**。

## 二、空行规范（定死，不再讨论）

### 2.1 唯一真源：`anyOutputEmitted`

- 本轮是否已经输出过任何可见内容，**只由 `index.mjs` 的
  `anyOutputEmitted` 一个变量表示**。
- 禁止任何新代码引入第二个行首/空行判据。具体禁止：光标位置探测、
  `\x1b[6n` 查询、按上一次写入内容结尾是不是 `\n` 来猜、各通道自己维护的
  布尔标志。
- 该变量在每轮输入开始时重置（`index.mjs:5134`），与 `promptCleared`
  同一位置、同一时机重置，两者永远成对。

### 2.2 责任方：**后来者补，先行者不留**

这是本规范最重要的一条，历史上的反转就是因为它没定死。

> **每一段输出负责在自己之前补足分隔，绝不在自己之后预留空行。**

- 段落结尾**不写**尾随 `\n\n`。
- 段落开头若 `anyOutputEmitted === true`，先补一个 `\n`，再写自己的内容。
- 若 `anyOutputEmitted === false`（本轮第一个输出），**不补**任何前导空行。

这条规则的好处是无状态可推：任意两段之间恰好一个空行，且首段永远贴着提示符，
不需要知道上一段是谁、也不需要知道下一段还有没有内容。当前
`writeSideChannel`（`index.mjs:1252`）已经是这个形状，把它推广到所有通道即可。

### 2.3 段间空行数量表

| 相邻关系 | 空行 | 依据 |
|---|---|---|
| 提示符 → 本轮第一段（任意类型） | 0 | `anyOutputEmitted === false` |
| 正文 → 工具调用行 | 1 | `bc0f3d47` 已确认 |
| 工具调用行 → 工具结果 | 0 | 结果是调用的延续，视为同一视觉块 |
| 工具结果 → 正文 | 1 | `bc0f3d47` 明确补的就是这一处 |
| 工具调用行 → 下一个工具调用行 | 1 | 并行调用之间要可数清个数 |
| 正文段落 → 正文段落 | 1 | markdown 语义，由 `stream-md` 自己保证 |
| 思考块 → 正文 | 1 | 思考是独立视觉块 |
| 最后一段 → 新提示符 | 1 | 由画提示符方负责，不由内容方预留 |

**任何不在此表内的相邻关系，默认 1 个空行。** 需要 0 或 2 的必须先改本表。

### 2.4 硬禁项

- 禁止 `\n\n` 字面量出现在输出拼接里（用「后来者补」代替）。
- 禁止在 `agent.run` 结束路径上无条件 `emit('\n')`（`1d925608` 删掉的就是
  这类残留空行，别再加回来）。
- 禁止在 flush 的尾段加 `\n`（`97f97f6a`、`5b1efabe` 两次都为此返工：
  尾段加 `\n` 会凭空多一空行，因为下一段还会按 2.2 再补一个）。

## 三、前缀与视觉层级

当前前缀符号散落在代码和 prompt 文案里（`core/prompts.mjs:39` 写了 `⎿`
和 `❯`，`core/teams.mjs:217` 自己用 `●`/`○`），没有集中定义。规范如下。

| 角色 | 前缀 | 颜色 | 说明 |
|---|---|---|---|
| 用户输入 | `❯ ` | `claude`（品牌橙） | 唯一使用品牌橙做前缀的地方 |
| AI 正文 | `⎿` | `dim` | 灰，与输入区分 |
| 工具调用 | `●` | 语义色（见四） | 按状态着色 |
| 工具结果 | `  ⎿ ` | `dim` | 缩进 2 空格，视觉从属于调用行 |
| 思考 | `✻`（或现有） | `reasoningPrefix` | 暖灰 + 斜体 |

规则：

- **缩进只有两级**：0 和 2。工具结果、列表续行用 2 空格。禁止 4 空格、
  禁止按嵌套深度递增缩进——手机屏宽 40 余列，多级缩进会把内容挤成竖条。
- **前缀符号必须集中定义**，见第五节的落地项。禁止在业务代码里写字面量
  `'●'`。
- 一个视觉块只有第一行带前缀，续行用等宽空格对齐，不重复前缀。

## 四、颜色规范

### 4.1 现状问题（必须收敛）

体检发现**四套独立的颜色表，用了三种不同的色彩深度**（24-bit / 8-bit / 4-bit）：

| 位置 | 定义 | 色彩深度 |
|---|---|---|
| `index.mjs:94` | `C` | 24-bit truecolor（`38;2;R;G;B`） |
| `core/markdown.mjs:4` | `C` | 4-bit ANSI（`\x1b[31m` 等） |
| `core/mini-highlight.mjs:13` | `C` | 8-bit 256 色（`38;5;N`） |
| `core/onboarding.mjs:7` | `C` | 4-bit ANSI |

后果是**同一个"红"在正文里和在 markdown 渲染里不是同一个红**：
`index.mjs` 的红是 `rgb(255,107,128)`（柔和粉红），`markdown.mjs` 的红是
终端主题的 `\x1b[31m`（随用户配色变化，可能是纯红）。用户看到的颜色不一致
不是错觉。

### 4.2 语义色板（单一真源）

以 `index.mjs:94` 的 truecolor 定义为准，其余三处全部改为引用它。

| 语义 | 值 | 用途 |
|---|---|---|
| 品牌 | `rgb(215,119,87)` | 仅用户提示符 `❯`、启动 logo。**不用于状态** |
| 成功 | `rgb(78,186,101)` | 工具成功、diff 增行 |
| 警告 | `rgb(255,193,7)` | 降级、重试、非致命 |
| 错误 | `rgb(255,107,128)` | 工具失败、diff 删行 |
| 信息 | `rgb(177,185,249)` | 路径、文件名、链接 |
| 思考 | `rgb(150,140,125)` + 斜体 | 仅 reasoning |
| 弱化 | `dim` | 前缀、时间戳、次要说明 |

### 4.3 用色纪律

- **一屏内彩色 token 不超过 3 种**（不含 dim）。手机小屏彩虹化会直接
  丧失层级——颜色多了等于没有颜色。
- **状态色只用于状态**，不用于装饰。禁止「这行重要所以标黄」。
- **正文默认无色**。信息层级优先用留白和前缀表达，颜色是最后手段。
- 禁止新增 4-bit ANSI（`\x1b[3Xm`）和 8-bit（`\x1b[38;5;Nm`）颜色；一律
  用 truecolor。前两者会随终端主题漂移，是「同一个红不是同一个红」的根因。
- 禁止背景色，除了 `claudeBg`（仅 logo）。手机端背景色块在深色主题下
  常糊成一团。

## 五、落地项（本次不改代码，只列出偏差）

按任务要求，本次是体检 + 规范制定，不动实现。以下是当前实现与本规范的
偏差，按优先级排列，供后续任务派活：

1. **P0 · 颜色表四份合一**。`core/markdown.mjs:4`、`core/mini-highlight.mjs:13`、
   `core/onboarding.mjs:7` 三处 `C` 改为从统一模块 import。建议新建
   `core/theme.mjs` 导出色板 + 前缀常量，`index.mjs:94` 的 `C` 也改为引用它。
   风险：`markdown.mjs` 现用 4-bit，换 truecolor 后视觉会变（变得更柔和、
   更一致），需要肉眼确认一遍。
2. **P1 · 前缀常量化**。`core/teams.mjs:217` 的 `'●'`/`'○'` 字面量、
   以及其他散落前缀，改引用 `core/theme.mjs`。
3. **P1 · 空行责任方统一**。`stream-md` 的 flush 路径目前是「尾段不加 `\n`」
   （已符合 2.2），但正文段间空行仍由 markdown 语义间接产生，未走
   `anyOutputEmitted`。建议让所有通道统一走一个 `emitBlock()` 包装，
   由它按 2.2 补前导换行，彻底消灭第二判据。
4. **P2 · 写一个排版回归测试**。这是防止第五次返工的关键：把 2.3 的表格
   变成断言（构造「正文→工具→结果→正文」序列，断言输出里
   `\n\n\n` 从不出现、且每个接缝恰好一个空行）。没有这个测试，规范只是
   文档，下次还会被改。
