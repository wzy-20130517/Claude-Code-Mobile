## 一、做了什么

### 1. 装齐官方全生态包（116 个）

```
npm 上 dsh-base bundle 的全部包 → 逐个安装
版本统一到 0.1.6-alpha.2（插件生态主战场）
```

**踩的坑**：
- npm 的 `latest` tag 指向老版（0.0.1-rc.1），新版在 `alpha` tag
- 混装两个版本线会出 `does not provide an export` 错误
- 3 个包装不了：`dsh-api-gateway` / `dsh-typert-registry`（依赖未发布的 `dsh-type-meta`）、
  `dsh-subprocess-local`（node-pty 原生编译失败）

### 2. 宿主服务从 2 个扩到 **19 个**

| 服务 | 来源类 |
|---|---|
| `ctx.llm` | LlmRuntime |
| `ctx.settings` | SettingsProvider |
| `ctx.timer` | TimerService |
| `ctx.credentials` | CredentialProvider |
| `ctx.subprocess` | SubprocessRuntime |
| `ctx.webServer` | WebServer |
| `ctx.systemPrompt` | SystemPrompt |

| `ctx.skills` | SkillRegistry |
| `ctx.fs` | LocalFileSystem |
| `ctx.shell` | ShellExecutor |
| `ctx.agents` | AgentRegistry |
| `ctx.jobs` | LocalJobRegistry |
| `ctx.sessions` | SessionStore |
| `ctx.sessionProjections` | SessionProjectionRegistry |

| `ctx.goals` | GoalService |
| `ctx.web` | WebRuntime |
| `ctx.sandbox` / `ctx.sandboxPolicy` | SandboxProvider / SandboxPolicyService |

外加 Cordis 核心 18 个 API（logger/on/effect/plugin/inject/...）。

**依赖顺序（踩过坑）**：
- `SystemPrompt` → `ToolRuntime`
- `SessionProjections` → `GoalService`
- `fs` 要用 `LocalFileSystem`（实现类），抽象 `FileSystem` 会先占名导致冲突

**关键发现**：`WebServer` 的监听在 `[Service.init]` 钩子里，
必须 `ctx.plugin(WebServer, config)` 挂载（`new` 不触发 listen）。

### 3. fiber 状态验证（inject 语义）

**关键发现**：cordis 的 `inject` 是"等待服务就绪"——依赖缺失时插件**挂起**而非报错。
所以"加载成功"≠"在工作"，要看 fiber 状态：

```
fiber.state = 2  → ✅ 活跃
fiber.state = 0  → ⚠️ 挂起等待（缺依赖）
```

实测 7/7 插件 state=2（补了 skills 服务后，之前挂起的 plugin-guide 也激活）。

### 4. 功能性验证（不只是"能加载"）

**从"插件活跃"到"能力可用"的验证链**：

```js
// ① 工具注册验证
const tools = host.get('tools')
tools.schemas()
// → [{name:'read'}, {name:'write'}, {name:'edit'}, {name:'bash'}]

// ② read 工具实际执行
const exec = tools.resolveExecution('read', { file_path: 'x.txt' }, {})
await exec.execute({ file_path: 'x.txt' }, {})
// → { path: '...', lines: [{number:1, text:'line1'}, ...], totalLines: 3 }

// ③ bash 工具实际执行 shell
const exec = tools.resolveExecution('bash', { command: 'echo hi', description: 'test' }, {})
await exec.execute({ command: 'echo hi', description: 'test' }, {})
// → { exitCode: 0, stdout: { text: 'hi\n' } }
```

**发现并修复的问题**：官方服务分「抽象 seam」和「本地实现」两类，
之前用的 `ShellExecutor` / `SubprocessRuntime` 都是**抽象类**（只有 constructor），
导致 `dsh-tool-bash` 报 `ctx.shell.resolve is not a function`。

修复链：
```
ctx.shell.resolve 不存在
  → 换 LocalBashExecutor（@deepseek-ai/dsh-bash-local@0.1.6-alpha.2）
  → npm latest 是依赖未发布包的老版，必须显式指定版本
  → ctx.subprocess.spawn 不存在 → 换 LocalSubprocessRuntime
  → node-pty 编译失败 → --ignore-scripts 绕过
  → ✅ bash 工具真执行
```

### 5. provider 双后端支持

| 后端类型 | 判定方式 | 例子 |
|---|---|---|
| **shim** | `adapter.config.profiles()` 存在 | dsh-account-pool |
| **webEndpoint** | 实际探测 `GET /<id>/v1/models` 返回 200 | dsh-freeroute |

**踩的坑**：一开始凭约定瞎拼 webEndpoint，把 shim 型也误判了。
改成**实际探测**后正确。

## 二、验证结果（有证据）

### 端到端测试

```bash
# 1. freeroute 门面接入（CCM 视角）
$ curl :8790/p/freeroute/v1/models -H "Authorization: Bearer dsh-local"
{"object":"list","data":[{"id":"auto","object":"model","owned_by":"_"}]}   ✅ 200

# 2. freeroute chat 端点
$ curl :8790/p/freeroute/v1/chat/completions -d '{"model":"auto",...}'
{"error":{"message":"没有可用的免费上游：请先在 设置 → freeroute 中启用并配置至少一个 API Key"}}
# ↑ 这是插件自己的业务错误（没配 Key），说明链路完全通了 ✅

# 3. account-pool 未就绪时的正确提示
$ curl :8790/p/workbuddy/v1/models
{"error":"provider workbuddy 无可用后端（shim 未就绪且无 webEndpoint）"}   ✅

# 4. 鉴权
$ curl :8790/p/freeroute/v1/models -H "Authorization: Bearer wrong"
{"error":"unauthorized"}   ✅ 401
```
